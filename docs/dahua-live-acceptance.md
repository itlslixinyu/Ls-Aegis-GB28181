## 实际问题与处理

1. 档案、注册、目录和媒体分别验证。最终同步获得“地库出入口”通道；此前旧通道编号返回404，不能以旧目录继续点播。
2. TCP主动可建立连接，但没有收到媒体；不将连接成功报告为视频成功。用户明确授权后，通过Windows管理员确认创建限定持久规则 `Ls-Aegis-Dahua-RTP-192.168.31.234`：只在Private网络允许来源192.168.31.234的UDP40000～40099。防火墙保持开启，未放行其他来源。切换UDP后约2秒收到真实PS/RTP。
3. 该固件H.265流在当前ZLMediaKit/浏览器组合出现参数集及缓冲错误，最终使用H.264并保留原分辨率。不是所有H.265设备都不可用：既有海康H.265同时播放正常。
4. G.711A对应FLV音频类型7，mpegts.js不支持。原错误回调立即销毁播放器，解码器继续使用已销毁事件发送器，产生用户日志中的 `null.emit`。现在将错误处理延迟到下一任务，并检查播放器身份及组件存活；重建前清除旧媒体元素源和错误状态。只重试一次视频降级，迟到错误不能重建已关闭播放器。
5. 标准 `streamnumber` 单独发送时，这台大华忽略子码流选择，仍返回2560×1440。补充同值 `streamprofile` 后，实际切换为704×576；海康仍使用原有属性正常播放。不能只凭下拉框文字宣称码流已切换。
6. 编码单项修改和界面保存期间曾发生其他字段回退；未据此认定用户修改配置。最终在同一短请求中明确主、子视频和音频8个字段，再次回读确认H.264/AAC8000Hz保持。过长的完整编码GET请求未成功，不作为配置已保存的证据。

## 2026-11-05 主码流花屏复查

大华 DH-IPC-HFW1433M-A-IL2，固件 2.860.0000000.40.R，GB28181-2016 / UDP。花屏时段媒体节点报告 RTP 丢包。主码流调整前的约 12 秒抓包收到 3757 包，另有 72 个序号缺口（约 1.9%）。仅将主码流固定码率由 3072 调至 2048 kbps，回读确认仍为 H.265 + G.711A、2560×1440、25 fps，子码流保持原配置。调整后同长度样本收到 2664 包，序号无缺口。网页 H.265/AAC 流通过约 25 秒 FFmpeg 严格解码。浏览器首次复测仍短暂出现花屏和缓冲，随后一次预览在播放进度约 20 秒时截图正常。持续稳定性仍待验证，当前证据未定位丢包发生在哪个链路环节。

### 180 秒连续预览复现

同一设备、固件及 GB28181-2016 UDP 配置，主码流 2048 kbps。浏览器连续预览 180 秒，间隔截图在第二个采样点再次捕获花屏和缓冲，随后画面恢复。同期 Linux 媒体容器 eth0 按端口及 SSRC 采集，收到 36927 个唯一 RTP 包、3569 个序号缺口（约 8.81%，560 组），AF_PACKET 监测 socket 丢包计数为 0。媒体服务同期报告 RTP 丢包，容器 UDP RcvbufErrors 为 0。问题已出现在媒体容器的网卡入口，仍需与同一会话的 Windows 物理网卡抓包对照，区分局域网侧与 Windows/Docker 转发侧。截图、抓包统计和浏览器日志保留在本机临时目录。

补充复测：同一 UDP 点播的另一段 140 秒容器入口采样收到 29708 包，1816 个序号缺口（约 5.76%），抓包 socket 无丢弃。Windows 普通权限无法调用 PktMon，复测结束时尚未取得同一会话的 Windows 物理网卡抓包。TCP-PASSIVE 对照由平台的设备忙保护拒绝，设备传输配置未被更改。

原生 ZLMediaKit 官方 CI 构建 Windows_master_2026-11-02，提交 fb3265725f0880da1f52a3cc6e6eb04bbc327fa3。下载包 SHA-256 与 GitHub Actions 官方摘要一致。先在隔离端口重放先前采集的国标 PS 样本，确认识别 2560×1440 H.265 和 PCMA 8 kHz。正式切换后，RTP 在 192.168.31.197 直收，HTTP 管理端口只监听 127.0.0.1:18080。旧 Docker 媒体容器保留为 ls-aegis-media-docker-backup，FFmpeg 工作容器使用原名但无网络和端口映射。原录像目录保持挂载，旧 MP4 的 HTTP 读取已通过。
